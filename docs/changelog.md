## 2026-08-04. Corrected `corresponding_author` on 12 records where it had been misattributed to a non-corresponding co-author

Surfaced directly by building `/institutions`: displaying `corresponding_author` prominently as the real outreach-contact target made a pre-existing data problem visible. This is the same "second systemic pattern" `sources/author_lab_search_2026-07-11.md` had already flagged and partially fixed (~20 records) -- it was never fully closed out.

**Method**: for every core record with both `corresponding_author` and a linked publication, compared the field's surname(s) against the first and last author of that publication. 120 records had both fields; 34 contained the first author's surname, 72 contained the last author's (often both, unremarkable). The 23 that contained the first author's surname but *not* the last author's were the real candidates -- a signal, not proof, since a first author genuinely is sometimes the corresponding author. Each of the 23 was individually re-verified against its paper's actual PMC full-text `<corresp>`/author-notes block (via NCBI E-utils `elink`/`efetch`, one record at a time -- batched `elink` calls with multiple PMIDs returned incorrect merged link sets and had to be abandoned for per-PMID requests) or, where no PMC full text exists, the PubMed record's own author-affiliation email.

## 2026-08-04. Repointed `/institutions` at real outreach-response tracking instead of public-data completeness

Follow-up to this same day's `/institutions` build, per direct feedback: the original completeness bar measured how much clinical metadata is already public per institution, useful context but not what's needed to decide who to partner with. What actually answers that is how many institutions have replied to direct outreach with real, previously-unpublished clinical metadata (radiation-treatment status, recurrence, outcome, etc.) -- a fundamentally different thing from anything derivable from `/data/*.json` itself.

- **`outreach/status.json`** (new): one entry per core dataset (138 total), a hand-maintained log of real contact attempts and their outcomes. Seeded at `not_contacted` for every dataset as of today, since outreach has not yet begun -- nothing here is inferred or placeholder, matching this project's "never fabricate" standard applied to a new kind of fact (what actually happened when someone was emailed, not what a source document says). **`outreach/README.md`** documents the schema, the six-state status enum (`not_contacted` -> `contacted` -> `responded_declined` / `responded_no_new_data` / `responded_partial_data` / `responded_full_data`), and the update convention (hand-edited, same as `/data/*.json`, no live backend).
- **`website/lib/data.ts`**: `getInstitutionSummaries()` now loads `outreach/status.json` and rolls it up per institution (contacted / responded / data-received counts, broken out by exact status). The prior public-data-completeness checklist (`CLINICAL_FIELDS`) is kept, but demoted to per-dataset "what's not yet public" context inside each expanded card -- useful for drafting the actual ask, no longer the headline metric. Institutions now sort by outreach signal first (data received, then responded, then dataset count as a tiebreak) instead of dataset count alone.
- **`website/components/InstitutionsExplorer.tsx`**: the completeness bar now shows the fraction of an institution's datasets with clinical metadata received directly, with a Contacted/Responded/Data-received readout beneath it; sort options changed to lead with "Data received" and "Responded". Each dataset in an expanded card now shows its outreach status badge and, once populated, its contact log.
- Verified: `npm run build`, `npm run lint` (both clean), and two headless-browser passes -- one against the real all-zero state (confirms `0/N datasets (0%)` renders correctly with no errors) and one against a temporary, reverted-before-commit test entry (confirms the bar fill, sort-to-top, status badge, and contact-log line all render correctly once real data exists).

## 2026-08-04. Built `/institutions`, a source-institution browser, as the first step toward planned clinical-metadata outreach

Motivated by a new lab goal: contacting the institutions behind these public deposits to request clinical metadata (radiation-treatment status specifically, plus general gaps like recurrence/outcome data) that didn't make it into the public deposit. Before any outreach, the raw `institution` field needed to be organized -- reading it record-by-record, it's extracted verbatim from each dataset's own source metadata, so the same real-world institution is frequently split across several strings (e.g. `UCSF` / `University of California San Francisco` / `University of California, San Francisco` -- 3 variants, 13 records; the Toronto Princess Margaret/UHN group -- 5 variants, 15 records).

- **`website/lib/data.ts`**: added `getInstitutionSummaries()` plus a presentation-only `INSTITUTION_ALIASES` canonicalization map. Only unambiguous same-institution variants (punctuation, abbreviation, a documented parent/division relationship) are merged -- multi-institution collaboration strings that combine a *different* set of partners per record are deliberately left distinct rather than folded into one member, since collapsing them would misrepresent which collaboration actually produced that record. This never modifies `/data/*.json`; every card on the new page still shows its underlying raw name variants. Corpus-wide effect: 92 raw institution strings collapse to 72 real institutions, 11 of which had 2-5 variants each.
- **`website/app/institutions/page.tsx`** + **`website/components/InstitutionsExplorer.tsx`** (new): a searchable, sortable (by dataset count, patient count, completeness, or name) card view, one per institution. Each card shows a **clinical-metadata completeness bar**, computed from a fixed 7-field checklist (WHO grade breakdown, primary/recurrent status, molecular subtype, outcome/survival data, brain invasion, sex distribution, age distribution) chosen because it applies broadly across modalities -- radiation-timing fields were deliberately excluded from this score since they only apply to a subset of cohorts and would unfairly penalize institutions whose datasets were never about radiation. This is explicitly labeled as "what's public so far," not a measure of institution responsiveness -- outreach-response tracking (contacted / replied / data received) is a follow-up, not built yet. Expanding a card lists every dataset with a per-record "Missing: X, Y" line, precomputed server-side from the same checklist (`missingFieldsById`) so the client component never duplicates the field-presence logic.
- Added `.completeness-track`/`.completeness-fill` to `globals.css` (a plain hairline track with an accent fill, matching this design system's instrument-panel restraint) and an `/institutions` entry to the nav.

Verified: `npm run build` (203 static pages, including the new page), `npm run lint` (0 errors), and a full headless-browser pass (Playwright) -- card count (72), search filter, and dataset-expansion all behave correctly, zero console errors.

**Not yet built** (intentionally deferred, see the motivating discussion): drafting or sending actual outreach emails, and persisted outreach-status tracking (contacted/replied/partner) per institution -- both need a decision on what to prioritize first (RT-status requests vs. general clinical gaps) before they're worth building.
